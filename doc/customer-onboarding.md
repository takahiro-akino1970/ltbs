# 得意先の発注利用許可・初期管理者登録方針

## 1. 位置付け

2026年10月15日の協議内容を、次回の実装に向けて記録したものです。
本書は設計方針であり、認証・利用許可・メール送信などが実装済みであることを意味しません。
合意した動作と、実装前に確定するデータ構造の案を区別します。

## 2. 合意した基本方針

- すべての得意先が発注機能を利用できるわけではなく、admin側で対象得意先に利用許可を与える。
- 利用を許可した得意先宛てに、初期管理者登録用の一時URLをメール送信する。
- 一時URLや招待トークン、そのハッシュを管理する招待用テーブルは設けない。
- URLのクエリに得意先コード、有効期限のタイムスタンプ、署名を含める。
- 得意先コードと有効期限を署名対象とし、改ざんを検知する。
- 有効期間はconfigで管理する。初期値は60分を想定し、実装時に設定する。
- 登録画面の表示時と、登録フォームの送信時の両方で検証する。
- 登録するのは発注側の得意先管理者アカウントであり、利用者がログインIDとパスワードを設定する。
- 対象得意先に既存の管理者アカウントがある場合は初期登録を拒否する。
- 登録成功時に得意先専用ログインURLを作成する。
- ログイン前の得意先表示は専用URLから行い、認証後の所属得意先はアカウント情報から決定する。
- 得意先コードや公開キーをCookie・localStorageに保存して、認証・認可の根拠とする方式は採用しない。

## 3. 操作フロー

### 3.1 admin側

1. 得意先を選択する。
2. 発注機能の利用を許可する。
3. 送信先メールアドレスを確認・設定する。
4. 得意先が利用可能で、初期管理者が未登録であることを確認する。
5. 設定した有効期間に基づき、発注側ドメインの署名付き一時URLを生成する。
6. 招待メールを送信する。

利用許可の保存とメール送信の成否は別に扱う。
メール送信失敗を成功として表示せず、未登録の得意先には再送できるようにする。
メール送信を非同期にするかどうかは実装時に決定する。

### 3.2 メール本文

記載する情報：

- 得意先名
- 得意先管理者アカウントの登録案内
- 登録用の一時URL
- 有効期限の日時
- 登録完了後は一時URLを利用できない旨
- 心当たりがない場合の連絡先

**得意先コードは本文の独立した項目として記載しない。**
ただし、一時URLのクエリには含めるため、URLを読めばコードが見えることは許容する。
パスワードはメールに記載しない。

### 3.3 発注側の初期登録

一時URLの例（パス・パラメーター名は案）：

```text
https://order.example.jp/register?customer_code=CUST-001&expires=...&signature=...
```

検証に成功した場合だけ、サーバー側で得意先コードから取得した得意先名と登録フォームを表示する。
登録フォームではログインID、パスワード、確認用パスワードを入力する。
管理者名を入力項目に含めることも検討する。

登録確定時には同一トランザクションで次を行う。

1. 対象得意先の利用設定レコードをロックする。
2. 利用許可と初期登録状態を再確認する。
3. 得意先管理者アカウントを作成する。
4. 得意先専用ログインURL用のランダムな公開キーを生成・保存する。
5. 初期登録完了日時を保存する。

登録成功後は専用ログインURLを案内する。
完了メールでもURLを通知する案とし、通知失敗によって登録済みアカウントを作り直さない。
パスワードはLaravelのパスワードハッシュ機能で保存し、平文では保存・通知しない。

## 4. 検証順序

登録画面のGETと登録処理のPOSTの両方で、次の順序で検証する。

1. **必須パラメーターと形式**：得意先コード、有効期限、署名が存在し、想定形式であること。
2. **有効期限**：サーバー時刻を基準として期限内であること。
3. **署名**：得意先コード、有効期限などの署名対象が改ざんされていないこと。
4. **得意先の状態**：対象得意先が存在し、利用可能であること。
5. **発注機能の利用許可**：admin側で許可されていること。
6. **初期登録状態**：初期管理者が未登録であること。

期限を先に確認しても、その値は署名検証前には未検証の入力である。
署名検証が完了するまでは得意先情報を表示せず、登録も行わない。
署名対象のパラメーターを登録POSTまで引き継ぎ、GETでの検証を理由にPOSTの検証を省略しない。
画面を開いた後に期限切れになった場合も、登録POSTは拒否する。

登録時には入力値の検証、CSRF対策を行い、フォームから送られる所属得意先やロールを信用しない。
同時に複数の登録POSTが到着しても重複登録されないよう、
トランザクション・得意先単位のロックと、必要なDB一意制約を組み合わせる。
GETは表示のみとし、アカウント作成や登録完了状態の更新を行わない。

## 5. 署名・有効期間・残る制約

### 5.1 署名の実装方針

- 「シード」はサーバー側で管理する秘密の署名鍵とし、ブラウザーには渡さない。
- 単純な文字列連結の独自ハッシュではなく、Laravelの期限付き署名URLの仕組みを利用する。
- admin側で生成し発注側で検証できるよう、招待用の署名方式と鍵を一致させる。
- 招待署名のためだけに両環境の`APP_KEY`を共通化せず、招待専用鍵を使う案とする。
  LaravelのURL署名機構への適用方法と他用途への影響は実装時に確認する。
- URLは設定済みの発注側公開URLから生成し、任意のHostや転送先を入力で指定させない。
- 本番はHTTPSとし、署名付きクエリをアクセスログ・アプリログへ不用意に残さない。
- 登録画面からのReferer漏えいを防ぎ、不要な外部リソースを読み込まない。
- 招待メール送信・登録には適切な回数制限を設ける。

### 5.2 短い有効期間で受容する制約

招待URLを保存しないため、以下を完全には解消しない。
初期値60分程度の短い有効期間で影響を限定する方針とする。

- 再発行しても、旧URLはその有効期限まで有効である。ただし初期登録完了後は拒否する。
- 特定のURLだけを失効させる機能は持たない。得意先の利用停止によって登録全体を拒否することはできる。
- アカウントの存在だけを判定すると、削除後に未期限切れのURLが使える可能性がある。
  後述の初期登録完了日時を残す案では、削除しても初期登録を再開しない。

また、署名は改ざんを防ぐものであり、メールの転送・漏えいで
有効なURLを取得した第三者による先行登録を防ぐものではない。
短い期限はこれらのリスクを低減するが、個別失効や本人確認の代わりにはならない。

## 6. 情報保存のためのデータ構造案

以下のテーブル名・カラム名・型は提案段階で、確定したDDLではない。
既存の得意先マスタは`db_stsystem.customers`であり、
発注機能専用の利用設定はアプリ側に分ける案とする。
既存の`avail_flg`と発注機能の利用許可は別の状態として扱う。
新規テーブルには原則としてNULL許容の`deleted_at`を追加し、論理削除を前提に設計する。
明確に不要な理由がある場合のみ省略し、理由を記録する。

### 6.1 得意先ごとの利用設定：`customer_order_settings`

| 項目案 | 用途 |
| --- | --- |
| `customer_id` | 既存得意先ID。得意先につき1レコードとなるよう一意にする |
| `is_enabled` | 発注機能の利用許可 |
| `contact_email` | 招待・完了通知先 |
| `public_key` | 専用ログインURL用のランダムな公開キー。登録前はNULL、値は一意 |
| `initial_registered_at` | 初期管理者登録の完了日時 |
| `enabled_at` | 利用許可日時 |
| `enabled_by` | 許可したadmin側ユーザーID |
| `created_at` / `updated_at` | 作成・更新日時 |
| `deleted_at` | 論理削除日時。未削除時はNULL |

`initial_registered_at`は招待URLではなく、得意先の初期登録が完了したことを示す業務情報。
初期登録済みの場合と、既存管理者アカウントがある場合は、いずれも登録を拒否する案とする。
管理者アカウントの削除・無効化でこの日時を自動的にクリアしない。
再初期化が必要な場合は、通常の招待再送とは別の管理操作として仕様を決める。
利用設定が論理削除済みの場合は利用不可とし、未登録と見なして初期登録を再開しない。
初期登録済み判定では削除済みの利用設定・管理者アカウントも考慮する。
得意先単位の一意制約は維持し、再利用時は既存設定の復元を検討する。

### 6.2 発注側アカウント：`order_users`

| 項目案 | 用途 |
| --- | --- |
| `id` | アカウントID |
| `customer_id` | 所属得意先ID |
| `login_id` | 利用者が設定するログインID |
| `name` | 利用者名 |
| `password` | パスワードハッシュ |
| `role` | 得意先管理者／一般ユーザー |
| `is_active` | アカウントの有効・無効 |
| `remember_token` | ログイン状態保持を採用する場合 |
| `created_at` / `updated_at` | 作成・更新日時 |
| `deleted_at` | 論理削除日時。未削除時はNULL |

得意先専用URLで対象を限定するため、`customer_id + login_id`を一意とする案。
この場合、別得意先で同じログインID（例：`admin`）を使用できる。
削除済みアカウントは認証対象から除外する。
論理削除後のログインID再利用可否と復元時の衝突については実装前に確定する。
一意制約にNULL許容の`deleted_at`を単純に追加する方法では、
未削除レコードの重複防止を担保できないため採用しない。

現在の`users`はLaravel標準のひな型である。
発注側専用の`order_users`を新設するか、既存`users`を拡張するかは、
admin側との認証分離・ユーザー管理設計と併せて実装前に決定する。
招待用テーブルは不要だが、利用設定の保存先と、得意先に紐づくアカウントの保存構造は必要となる。

## 7. 得意先専用ログインURL

URL例：

```text
https://order.example.jp/t/{public_key}/login
```

- 公開キーから得意先を検索し、ログイン前の画面に得意先名を表示する。
- 公開キーは得意先コードから計算せず、十分な長さの暗号学的乱数で生成する。
- 公開キー自体には認証・認可の権限を持たせない。
- ログイン時はその得意先に所属するアカウントに限定して認証する。
- 認証後の所属はログインユーザーから決定し、URLやCookieの値で他得意先へ切り替えない。
- 発注機能の利用許可はログイン時だけでなく、認証後の業務リクエストでも確認する。

## 8. 実装前の確認事項と検証項目

未確定事項：

- アカウント保存先、admin側の認証との分離方法。
- ログインIDの一意範囲、文字種・長さ、管理者名の入力要否。
- 既存マスタのID型、得意先コードの一意性、変更時の扱い、メールアドレスの取得元。
- 利用停止・再許可、登録後の管理者再設定、専用ログインURL再発行の運用。
- メール送信方式、送信失敗時の再送操作、監査記録。
- 設定名と期限値の検証、招待署名鍵の配布方法、Laravel標準機構との接続方法。

最低限の検証項目：

- 正常な画面表示・登録・専用ログイン画面の得意先表示。
- 必須値不足・形式不正・期限切れ・得意先コード改ざん・期限改ざん・署名不正の拒否。
- GET成功後に期限切れ・利用停止・他リクエストで登録完了した場合のPOST拒否。
- 既存管理者がいる場合と初期登録完了済みの場合の拒否。
- 同時登録で管理者アカウントが重複しないことと、失敗時のロールバック。
- ログインID重複・パスワード不備・CSRF不正の拒否。
- メール送信失敗を明示し、登録済みアカウントを通知失敗で作り直さないこと。
- 専用URLの得意先と異なるアカウントでログインできないこと。
- 利用停止後、既存セッションからも業務機能を利用できないこと。
