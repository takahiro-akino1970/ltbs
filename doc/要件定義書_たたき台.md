# Land Transport Booking System 要件定義書（たたき台）

## 1. 文書概要

### 1.1 目的

陸送に関する発注依頼、受注、輸送状況、完了実績を一元管理し、発注者と陸送会社の連絡・確認作業を効率化する。

### 1.2 対象システム

- システム名：Land Transport Booking System（陸送発注管理システム）
- 対象業務：車両の陸送発注、受注、輸送管理、履歴管理、利用者管理
- 想定利用形態：Webブラウザを利用した業務システム
- 参考資料：[陸送発注.png](陸送発注.png)

### 1.3 本書の位置付け

画面モックから読み取れる範囲で作成した初期案である。業務ルール、外部連携、権限の詳細、帳票仕様は関係者ヒアリング後に確定する。

### 1.4 技術・配置方針

- アプリケーションはLaravel、Inertia.js、Vue.jsを使用する。詳細なバージョンはプロジェクトの依存関係定義に従う。
- PWAおよびPush通知は初期要件案であり、実装済みの機能ではない。採用範囲と配信方式は別途確定する。
- 発注側と受注・システム管理側は、同じリポジトリ・同じアプリケーションコードから別々のアプリケーション環境として配置する。
- 両環境は別のドメイン、ログイン入口、セッションを持ち、発注側・管理側それぞれに許可した機能だけを提供する。
- 発注・受注データは共通のMariaDBで管理する。アプリ環境を分けても、データベースを含む障害・侵害の影響範囲は完全には分離されない。
- DBスキーマ変更は共通DBに対してリリース時に一度だけ実行する。両アプリの異なるバージョンが一時的に共存する場合も考慮して変更する。

#### 1.4.1 利用サービスの初期方針

| 領域       | 推奨サービス・機能                       | 用途                                           | 必須／選択               |
| ---------- | ---------------------------------------- | ---------------------------------------------- | ------------------------ |
| 地図表示   | Google Maps Platform Maps JavaScript API | PWA上でGoogle Mapsを表示する                   | 必須                     |
| 地点検索   | Google Maps Platform Places API          | 地名・施設名・住所検索、候補表示、Place ID取得 | 推奨                     |
| 住所取得   | Google Maps Platform Geocoding API       | 選択地点の緯度・経度から住所を取得する         | 必須                     |
| ルート表示 | Google Maps Platform Routes API          | 距離、所要時間、経路を表示する                 | ルート機能を実装する場合 |
| API管理    | Google Cloudプロジェクト                 | API有効化、APIキー、課金、利用量監視を管理する | 必須                     |
| Push受信   | Service Worker、Web Push API             | PWAでPush通知を受信・表示する                  | 必須                     |
| Push認証   | VAPID鍵                                  | Web Pushの送信元を認証する                     | Web Push方式では必須     |
| Push送信   | バックエンドのWeb Push送信処理           | 発注・受注イベントに応じて通知を送信する       | 必須                     |

## 2. 想定利用者・権限

| 利用者                           | 主な役割                                                   | 想定権限                                                                   |
| -------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| 発注者                           | 得意先に所属して車両の陸送を依頼するユーザー               | 発注依頼の登録、検索、詳細確認、再発注、キャンセル、通知確認               |
| 陸送会社担当者（システム管理者） | 発注を受けて輸送を手配し、システムと利用者を管理する担当者 | 発注検索、受注、連絡通知、ステータス更新、得意先・アカウント・ユーザー管理 |

発注側と受注・システム管理側のアカウントおよびログイン状態は分離する。発注側ユーザーは所属する得意先の発注情報、陸送会社担当者は受注対象の得意先の発注情報と管理情報を参照できるものとする。陸送会社担当者が得意先ごとの初期アカウントを発行し、得意先管理者は自社に所属するユーザーを追加・管理できるものとする。ユーザー種別、組織所属、ロールの具体的なデータ構造は、認証・認可の実装前に確定する。

### 2.1 システムの機能区分

本システムは、同じ発注データを扱うものの、利用者と目的が異なる発注側機能と、受注・システム管理側機能に分ける。

| 機能区分                 | 利用者                                     | 目的                                                                                       | データ参照範囲                                       |
| ------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| 発注側機能               | 複数の得意先に所属する発注者・得意先管理者 | 陸送依頼の登録、依頼状況の確認、再発注、キャンセル、連絡                                   | ログインユーザーが所属する得意先の発注のみ           |
| 受注・システム管理側機能 | 陸送会社担当者（システム管理者）           | 複数得意先からの依頼受付、受注判断、輸送進行、完了管理、得意先・アカウント・権限・設定管理 | 自社が受注対象とする得意先の発注、全得意先の管理情報 |

発注側と受注・システム管理側は別のアプリケーション環境として配置し、それぞれ専用のドメイン、ログイン・ログアウト、パスワード再設定、セッションを持つ。ログイン状態を相互に共有せず、各環境では対応する利用者種別だけを認証する。画面やURLの分離に加え、すべてのデータ参照・更新でサーバー側の認可を行う。発注側ではログインユーザーの所属得意先をサーバー側で特定し、リクエストで指定された得意先IDだけを根拠に他社データへアクセスさせない。発注側の画面で得意先を選択することはなく、受注・システム管理側では受注対象の得意先を横断して依頼を管理できる。

### 2.3 アプリケーション環境の分離

発注側と受注・システム管理側は、同じソースコードからビルドしたアプリケーションを別々に起動する。環境ごとにURL、接続先設定、セッションCookie名・保存先、キャッシュの名前空間、ログ出力先、ファイル保存領域を分け、片方のログイン状態や一時データがもう片方に混在しないようにする。Laravelの暗号化機能を使ってDBに保存する値を両環境で読み書きする場合は、`APP_KEY`の分離によって復号できなくならないよう、暗号化データの所有環境と鍵の管理方法を別途設計する。

発注・受注データは共通DBを利用するため、一方のアプリ環境からの不正アクセスや脆弱性が共通DBに影響する可能性がある。各環境におけるサーバー側認可、入力検証、監査ログを必須とする。アップロードファイルを両環境から扱う場合は、共有保存先を使うか、所有側を定めた認可付きの受け渡し方式を設計する。

### 2.2 機能区分ごとの主なメニュー

| 機能区分                 | 主なメニュー                                                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| 発注側機能               | 発注依頼履歴、新規発注依頼、発注詳細、地点履歴、ユーザー管理、通知                                                               |
| 受注・システム管理側機能 | 発注管理（受注管理）、発注詳細、受注処理、輸送進捗、連絡通知、得意先管理、アカウント発行、ユーザー・ロール管理、マスタ管理、設定 |

## 3. 業務フロー

### 3.1 発注側（得意先）

1. ログインする。
2. 「新規発注依頼」を選択する。
3. 出発地（引取先）、到着地（納車先）、発注日・出発日、車両情報、担当者情報を入力する。
4. 地図または履歴から出発地・到着地を設定する。
5. 「依頼内容確認」で入力内容を確認する。
6. 発注依頼を登録する。
7. 発注依頼の登録完了を画面で確認し、陸送会社担当者（システム管理者）へPush通知が送信される。
8. 発注側の発注依頼履歴画面でステータスと詳細を確認する。Push通知により、発注管理画面を定期的に巡回しなくても受注状況の変化を把握できる。
9. 受注、完了、キャンセル、連絡通知などの更新をPush通知で受け取り、必要に応じて通知から対象発注の詳細画面を開く。
10. 必要に応じて再発注、キャンセル、陸送会社への連絡通知を行う。

### 3.2 受注管理側（陸送会社）

1. ログインする。
2. 受注管理側の発注管理画面で新規発注を検索・確認する。
3. 発注情報、出発地、到着地、車両、希望日時を確認する。
4. 受注する、または必要に応じて連絡通知する。
5. 受注処理の完了が発注側へPush通知される。
6. 輸送の進捗に応じてステータスを更新する。重要なステータス変更は発注側へPush通知し、電話・メール等による個別確認を減らす。
7. 発注者からの連絡・備考を確認し、対応履歴を残す。連絡通知を送信すると、発注側の対象ユーザーへPush通知される。

### 3.3 Push通知を利用した共通フロー

1. 発注登録、受注、輸送進捗の更新、完了、キャンセル、連絡通知などの業務イベントが発生する。
2. システムがイベントの対象者と通知内容を判定し、通知イベントを登録する。
3. バックエンドの非同期処理が、通知許可済みの対象端末へPush通知を送信する。発注登録やステータス更新の画面処理は、通知送信の完了を待たずに完了できる。
4. 利用者は通知タイトル・概要を確認し、必要に応じて通知から対象発注の詳細画面へ遷移する。
5. 通知を受け取れない場合や通知許可を拒否している場合は、画面内通知を代替手段として利用する。

Push通知により、発注者は受注・完了・キャンセルなどの変化を早期に把握でき、陸送会社担当者（システム管理者）は発注登録や連絡への対応遅れを抑制できる。なお、Push通知は補助的な連絡手段とし、正式な発注状態はシステムに保存された発注情報を正とする。

### 3.4 発注ステータス（暫定）

| ステータス | 説明                                   |
| ---------- | -------------------------------------- |
| 新規発注   | 発注者が登録した直後の状態             |
| 仮発注     | 発注内容が登録済みで、受注確定前の状態 |
| 受注済み   | 陸送会社が受注した状態                 |
| 発注完了   | 輸送が完了した状態                     |
| キャンセル | 発注が取り消された状態                 |

ステータスの名称・遷移条件・変更可能者は業務確認のうえ確定する。

### 4.2.1 Google Maps地点選択・住所反映

| ID     | 要件                                                                                                                       |
| ------ | -------------------------------------------------------------------------------------------------------------------------- |
| MAP-01 | 出発地・到着地それぞれに「Mapから」ボタンを表示し、Google Mapsの地点選択画面を起動できること。                             |
| MAP-02 | 地図を移動または拡大縮小し、地図上のピン、クリック地点、または検索結果から対象地点を選択できること。                       |
| MAP-03 | 地点選択後、選択した緯度・経度をもとにGoogle Maps PlatformのGeocoding機能で住所候補を取得できること。                      |
| MAP-04 | 取得した住所候補について、住所名、郵便番号、都道府県、市区町村、番地・建物名、緯度・経度をフォーム反映前に確認できること。 |
| MAP-05 | 利用者が住所候補を確認し「フォームに反映」を実行した場合のみ、選択中の出発地または到着地フォームへ反映すること。           |
| MAP-06 | 住所候補の各項目をフォーム反映後に手修正できること。手修正した場合は、地図選択値と手修正値を区別して保持すること。         |
| MAP-07 | 地図選択元の地点種別（出発地／到着地）を保持し、反対側のフォームへ誤反映しないこと。                                       |
| MAP-08 | Google Mapsから住所を取得できない場合、フォームへの自動反映を行わず、手入力へ切り替えられること。                          |
| MAP-09 | API通信失敗、APIキー不備、利用制限超過、住所候補なしの場合に、利用者が原因を把握できるエラーを表示すること。               |
| MAP-10 | 反映された住所と緯度・経度を発注確認画面で再確認でき、発注登録時に保存できること。                                         |

#### 住所反映の標準フロー

1. 利用者が出発地または到着地の「Mapから」を選択する。
2. システムがGoogle Mapsを表示し、地図の中心、検索欄、地点選択用のピンを表示する。
3. 利用者が地図上の地点を選択する。必要に応じてGoogle Mapsの検索候補から地点を選択する。
4. システムが選択地点の緯度・経度を取得し、Geocoding APIで住所候補を取得する。
5. システムが住所候補を表示し、利用者が内容を確認・修正する。
6. 利用者が「フォームに反映」を選択すると、対象フォームへ住所、郵便番号、緯度・経度を反映する。
7. 利用者は反映後の住所を手修正でき、最終確認画面で内容を確認して発注する。

### 4.5 受注・システム管理側機能：ユーザー管理（発注側の得意先管理者を含む）

| ------ | ---------------------------------------------------------------------------------------------------------------------------------------- |

| USR-02 | ユーザー名、メールアドレス、TEL、最終ログイン日時を管理できること。                                                                      |
| USR-03 | ログインID、パスワード、所属得意先、ロールを管理できること。ユーザーは原則として1つの得意先に所属すること。                              |
| USR-04 | 得意先管理者は自社のユーザーだけを管理でき、他得意先のユーザーを参照・変更できないこと。                                                 |
| USR-05 | 受注・システム管理側画面では、陸送会社ユーザーと得意先アカウントを管理できること。                                                       |

### 4.6 得意先・地点管理

| ID     | 要件                                                                               |
| ------ | ---------------------------------------------------------------------------------- |
| MAS-01 | 得意先を登録・検索・編集できること。                                               |
| MAS-02 | 得意先ごとに利用ユーザーを紐付けられ、得意先管理者が自社ユーザーを追加できること。 |
| MAS-03 | 引取先・納車先の名称、住所、担当者、TELを地点マスタとして管理できること。          |
| MAS-04 | 発注入力時に地点マスタおよび利用履歴から地点を選択できること。                     |

### 4.7 通知・連絡

| ID     | 要件                                                                                                           |
| ------ | -------------------------------------------------------------------------------------------------------------- |
| NTF-01 | 新規発注、受注、完了、キャンセル、連絡通知などのイベントを通知対象にできること。                               |
| NTF-02 | ヘッダーの通知アイコンから未読通知を確認できること。                                                           |
| NTF-03 | 通知タイトル、本文、対象発注、送信者、日時、既読状態を保持すること。                                           |
| NTF-04 | メール通知を行うか、画面内通知のみとするかを設定できること。                                                   |
| NTF-05 | 利用者が通知許可を与えた端末・ブラウザをPush通知先として登録できること。                                       |
| NTF-06 | Push通知の購読情報をユーザー単位・端末単位で管理し、ログアウト、購読解除、期限切れに対応できること。           |
| NTF-07 | 発注の登録、受注、完了、キャンセル、連絡通知などのイベントを契機に、対象ユーザーへPush通知を送信できること。   |
| NTF-08 | Push通知本文に、通知種別、発注番号、概要、詳細画面への遷移先を含められること。機密情報は本文に含めないこと。   |
| NTF-09 | Push通知の送信結果、失敗理由、再送回数、送信日時を記録できること。無効な購読情報は送信対象から除外できること。 |
| NTF-10 | 通知許可を拒否した利用者や非対応ブラウザの利用者にも、画面内通知などの代替手段を提供すること。                 |

## 5. データ要件（初期案）

### 5.1 発注情報

- 発注ID、発注番号、発注日時、発注者、得意先、ステータス
- 出発日時、到着日時または到着予定日時
- 出発地、到着地、ルート情報
- 車種、車台番号
- 車両番号画像、画像から読み取った車両番号候補、読み取り結果、確認・修正履歴
- 備考・特記事項
- 受注者、受注日時、完了日時、キャンセル理由
- 作成日時、更新日時、更新者

### 5.2 住所・地点情報

- 地点種別：引取先／納車先
- 名称、郵便番号、都道府県、市区町村、番地・建物名
- 緯度・経度
- Google MapsのPlace IDまたは選択地点識別子（取得できる場合）
- Google Mapsから取得した住所（原文）と、システム項目へ分解した住所
- 住所の入力元：地図選択／地点履歴／手入力
- 地図反映後の手修正有無、最終確認日時
- 担当者、TEL
- 得意先との紐付け、利用履歴

### 5.3 監査情報

発注情報およびユーザー情報の重要な変更について、変更前後、実行者、実行日時、操作種別を記録する。

### 5.4 PWA・Push通知情報

- ユーザーID、端末識別情報、ブラウザ情報、Push購読エンドポイント
- Web Pushの暗号化に必要な購読キー情報
- 購読開始日時、最終利用日時、購読解除日時、購読状態
- 通知イベントID、通知種別、対象発注ID、通知先ユーザーID
- 送信状態、送信日時、失敗理由、再送回数、既読日時
- 購読情報および通知履歴の削除・保持期間

Push購読情報は認証情報と同等に機微な情報として扱い、ログへの平文出力を禁止する。

## 7. 外部連携・前提

- Google Cloudプロジェクト：Google Maps PlatformのAPIを有効化し、APIキー、課金アカウント、利用量・エラー監視を管理する。
- Maps JavaScript API：PWAの地図表示、地図操作、地点選択に利用する。
- Places API：住所・施設検索、検索候補表示、Place ID取得に利用する。採用するAPIバージョンと取得項目は確定すること。
- Geocoding API：選択した緯度・経度から住所候補を取得する。住所コンポーネントからシステムの住所項目へマッピングする。
- Routes API：出発地・到着地間の距離、所要時間、経路を表示する場合に利用する。
- Google Maps APIキー：ブラウザ用キーをドメイン・API単位で制限し、秘密鍵をフロントエンドへ埋め込まない。キーの発行者、更新方法、利用量監視を定義する。
- 住所検索サービス：Google Mapsが利用できない場合の代替手入力を提供する。別の住所検索サービスへ切り替える場合は、住所項目のマッピングと利用規約を確認する。
- メールサービス：発注・受注・完了等の通知に利用する可能性がある。
- Web Push配信：PWAのService WorkerとWeb Push APIを利用する。バックエンドでVAPID鍵を管理し、Push購読エンドポイントへ通知を送信する。
- Firebase Cloud Messaging（任意）：Push配信基盤としてFCMを採用する場合に利用する。採用時はFirebaseプロジェクト、Cloud Messagingの設定、トークン管理、送信失敗時の無効トークン削除を定義する。
- Push送信処理：発注・受注等のイベントを契機に、バックエンドのキューまたはジョブから通知を送信する。画面の登録処理と通知送信処理は分離する。
- 画像読取サービス：車両番号画像から文字を読み取るOCRまたは画像認識サービスを利用する。採用サービス、認識精度、送信画像の保存・削除方針は確定すること。
- 画像保存先：車両番号の読取に使用する画像を保存する場合、保存先、アクセス制御、保存期間、削除方法を定義する。画像を保存しない場合は読取後に破棄する。
- 認証基盤：既存の社内認証やSSOを利用する場合は方式を確認する。
- アプリケーション：Laravel、Inertia.js、Vue.jsを使用する。実装構成はプロジェクトの既存構成に従う。認証・認可、通知、発注管理を独立したAPIサーバーとして分割することは本方針に含めない。

## 9. 業務ルール・要確認事項

1. 発注者と、陸送会社担当者（システム管理者）の正式な組織・権限境界。
2. 発注ステータスの正式名称、遷移図、各遷移を実行できるロール。
3. 「仮発注」と「新規発注」の業務上の違い、および受注前後の編集可否。
4. 発注キャンセルの期限、キャンセル可能者、理由の必須／任意。
5. 発注番号・発注IDの採番規則と重複防止方法。
6. 出発日時・到着日時の必須条件、過去日時の許可、タイムゾーン。
7. 車台番号の桁数・形式、車種マスタの管理者と選択肢。
8. 出発地・到着地の住所必須項目、地図検索の採用サービス、手入力との優先順位。
9. ルート詳細に距離、所要時間、経路、料金のどこまで表示するか。
10. 車両番号画像の対象、容量、拡張子、枚数、読取方式、画像保存の要否、保持期間。
11. 通知チャネル（画面、Web Push、メール等）、通知先、再送、既読管理。
12. PWAの対応ブラウザ・OS、インストール必須か任意か、オフライン時に許容する操作。
13. Push通知の許可拒否時の代替手段、通知文面、通知タップ時の遷移先。
14. 標準Web PushとFirebase Cloud Messagingのどちらを採用するか、VAPID鍵またはFCM認証情報の管理者。
15. Web Push配信基盤、送信レート制限、失敗時の再送方針、無効な購読情報の削除方法。
16. PWA・Push通知の採用範囲、共有DBに対するアプリ別DB接続権限、ファイル共有方式、暗号化鍵の管理方法。
17. 一覧の既定の並び順、1回あたりの取得件数、CSV出力・帳票出力の要否。
18. 既存の得意先、地点、車両、ユーザー情報とのデータ連携要否。
19. 同一発注の二重受注を防止する制御と、同時更新時の扱い。
20. 個人情報・車両情報の保持期間、削除・匿名化方針。

## 10. 受入観点（初期案）

- 必須項目未入力では発注依頼を登録できず、項目ごとのエラーが表示される。
- 正常な発注依頼を登録すると発注番号が発行され、履歴と詳細から確認できる。
- 発注者は権限外の他社発注を参照・編集できない。
- 陸送会社が受注すると、受注者・受注日時が記録され、発注者側で状態を確認できる。
- キャンセル済み発注は通常の受注処理に進められない。
- 発注詳細から出発地・到着地、車両、日時、ステータスを一貫して確認できる。
- 発注側で車両番号画像をアップロードすると、読み取った車両番号候補が表示される。
- 発注者が車両番号候補を確認・修正して確定でき、読み取り失敗時は手入力へ切り替えられる。
- 地図で選択した地点をフォームへ反映でき、住所情報として保存できる。
- 重要操作の履歴から、誰がいつ何を変更したかを追跡できる。
- PWAを対応ブラウザへインストールでき、Service Workerが登録される。
- 通知許可を与えたユーザーへ、発注イベントに応じたPush通知が届く。
- 通知をタップすると、認証状態を確認したうえで対象発注の詳細画面へ遷移できる。
- Push通知を拒否または解除したユーザーには、画面内通知などの代替手段が表示される。
- 期限切れ・無効なPush購読情報が検知された場合、以後の送信対象から除外される。
